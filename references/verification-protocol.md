# 验证通道协议（阶段 3.5 / 卡点 0 必读）

> 参考 startup-positioning 的 Verification Agent（V1）机制适配而来。其原始设计是：产出完成后 spawn 一个**未参与写作的独立 agent**，只读交付文件，按固定协议审计，产出验证报告，Critical 问题必须处理后才交付。「独立」的本质是**审计者不是作者**——对抗写作者的确认偏误。

## 何时执行

报告初稿完成后、交付用户前。**无条件执行**：即使用户授权「卡点全放」，被跳过的只是「暂停等用户确认」，验证本身与验证报告产出不可跳过。验证报告（verification-report.md）是正式交付物之一。

## 如何模拟「独立验证」（无并行 agent 环境的适配）

1. **只以写出的文件为唯一事实源**——不凭写作时的记忆为报告辩护；文件里没写的，视为不存在。
2. **切换为对立评审视角**——假设自己是一个第一次看到这份报告、且利益与作者相反的人，任务是找茬。
3. **逐项检查并留下证据**——每条检查项给出「文件 + 位置 + 原文」三级定位，不允许凭印象打勾。
4. **零发现视为可疑**——一份数万字的报告审完一个 Warning 都没有，说明审得不认真，重审。

## 通用检查（7 项，任何品类适用）

| # | 检查项 | 判定规则 |
|---|--------|---------|
| G1 | 无标签论断 | 每个数字、事实、结论必须带来源标签（[本人提供] / [已验证-来源] / [AI推测] / [AI结论]），无标签即 flag |
| G2 | 跨文件/跨章节矛盾 | 同一指标两处取值不一致；正文结论与表格数据打架；前后章节的假设互相冲突 |
| G3 | 数字闭合 | 每个定量主张的推导路径代入真实数字重算一遍，算不通即 Critical |
| G4 | 数据缺口声明 | 报告必须如实列出「不可得/未验证」清单；调研中提过但报告里消失了的缺口 = Critical |
| G5 | 概念级标注 | 未打样、未测试、未备案的部分必须显式标注「概念级，待验证」；概念稿写得像生产规格 = Critical |
| G6 | 陈旧数据 | 法规快照、市场数据、标杆数据超过其时效未标注日期的，flag |
| G7 | 伪交叉验证 | 同一来源（同一篇报道/同一数据平台）被当作「多方独立验证」重复引用，flag |

## 专属检查

完成通用检查后，按 `self-audit-checklist.md` 逐项打勾（该清单随每次纠偏持续生长）。

## 输出：verification-report.md 模板

```markdown
# 验证报告：{项目名}
*生成日期 | 验证范围：{交付文件清单}*

## 摘要
- Critical：{n} 条（误导决策级，必须处理）
- Warning：{n} 条（降低质量级，建议处理）
- Info：{n} 条（观察项）

## Critical
### {问题标题}
- 位置：{文件 + 章节}
- 问题：{描述 + 原文引用}
- 建议修复：{具体动作}

## Warning
（同上结构）

## Info
- {观察项}

## 验证清单
- [ ] G1 无标签论断  - [ ] G2 跨文件矛盾  - [ ] G3 数字闭合
- [ ] G4 数据缺口声明  - [ ] G5 概念级标注  - [ ] G6 陈旧数据
- [ ] G7 伪交叉验证
- [ ] self-audit-checklist 全部通过或显式标注
```

## 流程控制（Critical 的处理不新增门禁卡点）

验证发现的问题分两类处理，**不需要用户决策的不得停下来请示**（守住「全程最多停 2 次」的门禁哲学）：

- **(a) 事实/逻辑错误**（数字矛盾、来源缺失、标注遗漏）→ **自主修复后交付**，在验证报告中记录「发现→修复」闭环；
- **(b) 必须用户输入才能修**（缺企业真实数据、需要用户拍板的取舍）→ 不伪造答案，列入报告「待用户提供」清单，随交付一并呈现。

即使用户已授权全放，(a) 类修复与验证报告产出仍必须执行——全放跳过的是「停下来问」，不是「验证」本身。
